# V2 Owner Request-Handling Mockups

Created: **22 October 2026**.

Status: **Approved by the user; frontend prototype implemented with shared persisted mock data.**

The Owner is the admin-facing business role, not a fourth role. This selection comes from the [V2 backlog](../../BACKLOG.md) and handles the actions exposed by the customer frontend: direct bookings, custom quote requests, payment outcomes, and cancellation requests. It is not a full Owner management-system design.

The screens show illustrative driver/fleet records; full driver and fleet management are not selected for this initial Owner prototype.

## Workflow boundaries

- Standard priced customer bookings arrive directly in Bookings. They do not require an enquiry or manual quote.
- Only custom quotes and special requests enter Custom quotes.
- A custom quote must be accepted by the customer, with required sign-in/authorization, before conversion into a customer booking. The prototype includes customer quote acceptance in My requests and conversion into one booking.
- Driver assignment must respect category, capacity, availability, licence, registration, reservation overlap, and turnaround. In a frontend-only prototype these outcomes must be clearly simulated; production enforcement belongs to the future backend.
- Booking confirmation does not mark payment successful. Payment states come from provider evidence in production, and labeled mock records in a frontend prototype.
- Approving cancellation releases the relevant assignments but does not itself issue a refund. Refund amounts, eligibility, and provider workflow are still policy decisions, not locked by a mockup.
- Prototype policy: save an eligible assignment before confirmation; unpaid bookings may be confirmed. Refunds require approved cancellation and a recorded payment. Production policies still require backend enforcement.
- No email, booking confirmation, cancellation, financial transaction, or external write was performed to create these images.

## Design direction

Use the approved V2 customer palette and typography in an operational desktop shell: persistent Owner sidebar, compact header, filterable booking table, focused detail forms, and activity/payment summaries. All displayed people, identifiers, fares, schedules, provider references, and status counts are fictional design data.

The four images are connected screens, not competing style options. These are static desktop references. The runnable frontend adds responsive layouts and interactive request handling; full backlog delivery still requires backend integration and production verification.

## Generation

Generated using the built-in image generation tool. The approved customer review mockup supplied visual language for the first screen. The generated Bookings mockup then supplied the common Owner shell for the other screens. No legacy application visual source was used.
