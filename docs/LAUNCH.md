# Hosted acceptance and launch

Local checks validate application code and real PostgreSQL behavior in a disposable database. They do not validate a hosted Supabase project, its Auth/SMTP/Storage/Realtime services, CAPTCHA, or a payment provider. Complete the following with the real client’s staging project before launch.

## Project and owner

- Apply migrations 001–007 in order. Preserve already applied migrations and actual existing business records. Set the project URL/publishable key, server-only service key and actual organization UUID.
- Provision and verify the real owner using restricted Supabase administration, then bootstrap only that actual Auth user. Configure signup restrictions, password policy, exact HTTPS origins, email templates and custom SMTP as in README.
- Test successful/failed sign-in, password visibility, session refresh/expiry, sign out, recovery, invite links, expired/reused tokens and redirects. Disable a signed-in staff account and verify reads/writes fail immediately. Driver accounts must redirect away from management, with no operational data access.

## Operations, storage and security

- Create/edit/archive/restore actual client-approved staging driver, fleet, location, route, extra and customer inputs. Never seed demonstration records in the production project. Test uniqueness, cross-business references, stale edits, active archive restrictions and driver account activation/deactivation.
- Invite a genuine consenting staging driver. Confirm only its reserved profile links to the created Auth user, account access is driver-only, direct Auth-link writes are denied and invitation delivery failure revokes provisioned access. Test all staff roles and last-owner protection, including rejection of Owner promotion and unverified client identity.
- Validate the full pending → confirmed → in progress → completed flow, cancellation reasons and invalid transitions. Confirm seats, luggage, category, licence, registration and assignment compatibility. Test simultaneous driver and vehicle conflicts, turnaround buffers, back-to-back nonoverlapping intervals, trip overruns, cancelled reservations and immutable historical status/assignment/audit records.
- Verify the private Storage bucket, WebP size/MIME restrictions and tenant/role policies. Test genuine JPEG/PNG/WebP re-encoding, wrong formats, spoofed MIME, oversized images, invalid paths, another organization's uploads and publication/unpublication. Public signed media links expire after five minutes; unpublishing does not retroactively invalidate a link before expiry. Replaced images remain in Storage until an authorized retention process removes orphaned files.
- Test real PostgREST foreign-key embeds and all dashboard/report queries on the hosted project. A failed query must produce an error, not silently fabricated zero totals. New businesses should have zeros and meaningful empty states.
- Confirm Realtime publication and authorized events using two accounts/businesses. Reconnect after token refresh and access changes. GPS markers must appear only for authorized active trips with genuine received driver coordinates. Verify private Realtime snapshot authorization, consent/stop, stale/offline states, reassignment/terminal revocation and retention; route markers use actual stored coordinates. Test the optional OpenStreetMap tile connection and attribution. Confirm polling/manual refresh works when Realtime is unavailable.

## Payment verification and launch controls

- Stripe adapter code is implemented; genuine provider verification and approval are still required. Do not populate `verified_payments` using owner-entered payment labels, synthetic receipts or unverified events. Only the trusted signature-verifying provider integration may write these immutable events after validating the provider signature, event identity, actual booking/currency/amount, refunds and replay/idempotency. Client-facing payment success must remain unavailable until that integration is configured and verified.
- Reports intentionally exclude old manually entered `payment_status` labels. A completed booking or agreed fare is not revenue. Verify the dashboard remains zero without trusted provider events, and test actual signed charges/refunds only after a provider integration exists.
- Configure HTTPS, administrator MFA, hosting access, monitoring, incident response, backups and tested restores. Staff MFA and a full nonce-based CSP are not implemented. Current headers restrict framing/objects/base URLs and all user text is rendered through React; assess the client’s stronger security requirements before launch.
- Review privacy, consent, retention, data erasure and applicable UAE business requirements. Contact information is available only to active authorized portal staff; audit rows store identifiers and changed field names rather than personal-information snapshots. Archiving is not erasure. Define lawful deletion and media-retention processes for trusted project administrators.
